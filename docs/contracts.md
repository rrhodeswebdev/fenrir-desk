# Cross-plan contracts

Exact names, signatures, file paths and JSON shapes where modules meet. `SPEC.md` says what and why; this file says exactly how. Implement a contract exactly as written; a change to it lands in the same commit as the code and says so in the commit body. When this file and the spec or code disagree, stop and ask.

"Plan NN" below names the module group that owns a contract. The work itself is tracked as GitHub issues `[NN.x]` (index: `tasks/plan.md`).

## Directory context files

Every directory with its own responsibility gets a `CLAUDE.md` (Claude Code loads it automatically when working there) and a row in the root `CLAUDE.md` → **Directory Map**. The plan that creates a directory adds both, in the same commit as the directory's first code. Covered by the parent's file instead (no file of their own): pure test mirrors (`tests/<pkg>/`), asset-size folders (`png/`), build output.

Template (keep it under ~15 lines):

```markdown
# <path>/

<One sentence: what this directory handles.>

- Entry points: `<file>` (<what it exposes>), ...
- Pure vs shell: <which files are pure core, which do I/O>.
- Not here: <the nearest thing people would wrongly look for here, and where it lives>.
- Tests: `tests/<path>/`.
```

### Plan 04 — `fenrir.data.live`

```python
@dataclass(frozen=True, slots=True)
class Tick:
    ts: datetime; price: float; size: int; contract: str
@dataclass(frozen=True, slots=True)
class BuilderState: ...                     # current partial bar per contract
def empty_builder() -> BuilderState
def feed(state: BuilderState, tick: Tick) -> tuple[BuilderState, tuple[Bar, ...]]   # emits bars closed by this tick
def close_due(state: BuilderState, now: datetime) -> tuple[BuilderState, tuple[Bar, ...]]  # emits bars whose minute has ended
async def stream_bars(settings: Settings, contracts: Sequence[str], *, on_auth: Callable[[], None] | None = None) -> AsyncIterator[Bar]   # shell
# fenrir.data.lse
async def stream_ticks(settings: Settings, contracts: Sequence[str], *, on_auth: Callable[[], None] | None = None) -> AsyncGenerator[Tick, None]   # on_auth: each time the socket authenticates (#212)
class FeedStopped(Exception)               # fenrir.data.live: the feed's client stopped and will not reconnect by itself; .permanent (no key) = only a restart helps, otherwise retry with a backoff
```

`contracts` are front-month codes (`ESZ26`); `stream_ticks` subscribes to `lse_symbol` of each (`ES.F`) with `LSE.stream_async(reconnect=True)` and maps ticks back to the code. An empty `settings.lse_api_key` raises a permanent `FeedStopped` naming `FENRIR_LSE_API_KEY` before any client is built (never the SDK's `LSE_API_KEY` env fallback; `fetch_contract` raises `ValueError` the same way). It drops replayed ticks, ticks with no or a naive time, ticks with no volume (quotes) and ticks with a missing, non-finite or non-positive price, snaps the price to 0.25 and rounds `volume` (the per-trade quantity as far as the values show) to `size`. `price` is what LSE sends; every recorded tick has `price == bid` (docs/data-gate.md Item 3), which gate item 4 checks. `stream_bars` closes a minute at wall clock minus `LAG_GRACE` (2 s), checked every second, so lagging ticks still count, and drops a tick stamped more than `MAX_AHEAD` (5 s) past the wall clock; ticks dropped as ahead or late are counted and logged as one warning a minute at most. It yields closed bars only, never a partial one when the stream ends. The SDK reconnects after a drop (every 3 s) and logs each error event as a warning; when it stops instead (any error before auth: bad key, quota, or the key's one socket still held, e.g. by a half-open old connection the server drops later) `stream_ticks` raises `FeedStopped` with the server's last message; so does an `LSEError`. `on_auth` is registered as the SDK's `authenticated` callback, so it runs on the first connect and on each SDK reconnect, before any tick on that socket (`stream_bars` passes it through). A bar spanning a reconnect lacks the trades of the gap. Closing the stream closes the socket: LSE allows one per key. During the roll window `ES.F` may still carry the expiring contract under the new code; live takes no entries then (21.3).

### Plan 05 — `fenrir.rules.schema` / `loader`

`AccountRules` is a pydantic v2 model, `model_config = ConfigDict(frozen=True, extra="forbid", strict=True, allow_inf_nan=False)` (no `"4"` → 4, no inf/nan; ints still fill float fields), mirroring the rules YAML in `SPEC.md` → Rules exactly, plus `max_drawdown.locks_at: float | None` (profit above start at which the trailing floor stops trailing; `null` = never locks). Sub-models: `Drawdown(amount, trailing: Literal["end_of_day","intraday"], locks_at)`, `Consistency(max_day_pct)`, `Payout(max_pct_of_profit, split_pct, min_days, min_profit` (smallest request)`, min_day_profit = 0` (a day counts toward min_days only at or above it)`, max_amount: float|None` (cap per payout)`, max_payouts: int|None)`, `Phase(max_drawdown, daily_loss_limit: float|None, consistency: Consistency|None, min_trading_days: int = 0)` (shared base), `Evaluation(Phase)` adds `profit_target: float`, `Funded(Phase)` adds `payout: Payout` and `scaling: tuple[Tier, ...] | None` (`Tier(from_profit, max_minis)`, ascending from 0; the max size for the current profit, recalculated at session end; `None` = `contracts.max_minis`), `Session(flat_by, tz)`, `Contracts(max_minis, micros_per_mini)`, `Microscalp(max_profit_pct, hold_seconds)`, `Prohibited(microscalp, hft)`, `Commission(ES, MES, NQ, MNQ)`, `Costs(activation_fee, commission_per_side: Commission)` (no `eval_fee`: the price paid varies with coupons, so it is a user input, not a rule) (read a symbol with `getattr(rules.costs.commission_per_side, symbol)`). Top level: `firm, account, verified_on: date | None` (null = not yet verified, shown as stale; ISO strings accepted)`, source_url, automation_allowed, evaluation: Evaluation | None, funded: Funded, session, contracts, prohibited, costs`. Each phase rejects the other's field (`extra="forbid"`). The loader rejects duplicate YAML keys.

`periods.holdout` is `null` when `include_holdout` is false. `holdout_gap` is true when held-out `p_pass_and_payout` < 50% of tuning's. `PeriodResult`:

```json
{
  "start": "2019-01-02", "end": "2025-10-09", "attempts": 1700,
  "pass_rate": 0.31,
  "days_to_pass": { "median": 9, "histogram": [[1, 4], [2, 11]] },
  "failure_reasons": { "max_drawdown": 900, "flat_by": 3, "no_result": 20 },
  "payout_rate": 0.62,
  "median_days_to_payout": 14, "median_first_payout": 1250.0,
  "p_pass_and_payout": 0.19,
  "expected_gross_per_attempt": 87.5,
  "microscalp_flags": 4,
  "sample_equity": [ { "start": "2023-05-01", "outcome": "payout", "points": [["2023-05-01T13:31:00Z", 0.0]] } ]
}
```

`failure_reasons` keys are `"max_drawdown"`, `"flat_by"` and `"no_result"` (data ran out first); it counts every attempt without a payout. Hitting the daily loss limit is not a failure: that day halts and the attempt continues. `median_days_to_payout` counts from the attempt's start. `expected_gross_per_attempt` = mean over attempts of (payout or 0) − (activation_fee if passed); fee-free, because the evaluation price varies with coupons and is user data (`AccountChoice.eval_price`). Net per attempt = gross − that price, computed on read (`net_per_attempt`) and added by the API as `expected_net_per_attempt`; it is never in a cached report. `dll_on` records whether the daily loss limit was simulated (the user's choice, part of the key). One live/backtest rule: a new `Bracket` is rejected while a position is open. Medians are `null` when there is nothing to take a median of. `sample_equity` holds at most 6 attempts (2 passed+paid, 2 passed only, 2 breached; first by start date).

Server → client: binary frames of raw PTY output. On disconnect the server hangs up the PTY, gives the shell 1 s to pass SIGHUP to its jobs, then SIGKILLs its process group and every live process still in its session (session id = the shell's pid), listing and killing again until the session is empty (at most 10 rounds, logged if any remain; a process it may not kill, such as a setuid program, is skipped and logged by pid) so a job forking mid-kill is caught too; background, `nohup` and `disown` jobs die under any shell. The teardown runs to the end even if the handler is cancelled. Only a process that calls `setsid` leaves the session and outlives the disconnect, running as the PTY user with the same scrubbed environment; it is not tracked or killed.

Limit: only the last path component is never followed (the manifest and `data/jobs` excepted); a symlinked directory on the way (`data/results`, `bars/<series>/1m`, `rules/<firm>`) is still followed, so a regular file with the reader's extension in the link's target can be read, and a rules YAML error can quote such a file.

The secrets file `load_settings` reads is `$FENRIR_ENV_FILE` (default `.env`; `/var/lib/fenrir/.env` in the image); with `FENRIR_BIND_ALL=1` it never falls back to the repo `.env`, so with `FENRIR_ENV_FILE` unset it reads no file. A Bracket is rejected when halted, for sim/live while `day_start` is None, after another Bracket accepted on the same bar, or when a later Flatten/Cancel on the same bar replaces it (journalled as a rejection: the backtest never places it), while a sent entry is still working (22.1), while in a position, when the last bar in `Ctx.bars` is not the bar `on_bar` last saw (`bars[-1].ts + 1 min != last_seen`: "not the latest bar: no entry at an older bar's close", e.g. `decide` after a roll-window bar; #189), when the bar closes at or after `min(session.flat_by, "16:40")`, or when `fenrir.rules.pretrade.check` rejects it at the bar's close (including a qty that is not a positive whole number, e.g. NaN or 1.5 from the child's JSON); Flatten and Cancel always pass. Roll window (#170): the backtest loads no bars on a trading day `in_roll_window`, so live and backtest feed `step` the same bars around a roll: on those days the runner never calls `step` (so takes no entry) and never adds the bar to `Ctx.bars`, while `on_bar` still journals it, marks the position, checks drawdown, the daily loss limit and the safety margin, rolls the day and flattens at flat-by; the first bar after the window gets `Ctx.bars` ending with the last bars before it, exactly the backtest's slice. Warm-up (#79) must build `Ctx.bars` the same way. The window follows the hub's front month, which is the new contract from roll Thursday, so a position still held on the old contract (adopted by reconcile) is marked with the new contract's bars during the window; positions are normally flat by the roll. The safety margin day-halts (`halt_kind` "safety", until the current trading day) when close-mark equity is at or below `safety_level`. For sim and live, `day_start` sets today's opening balance (`day_start_balance` and `session.start`), which drives the daily loss room and the funded scaling tier, and the floor at the open (from `day_start.peak`, exact for `end_of_day` and `intraday` trailing and `locks_at`), which with it fixes the safety level's room; while it is None every Bracket is rejected with "today's opening balance unknown" (Flatten and Cancel pass), so a mid-day restart never trades on the balance at restart. The hub supplies both through `start`: today's journalled `opens`, else NinjaTrader's balance less its realized loss today (`Start.realized_today`; #211, "Starting sim and live" below); one without the other is not enough. The open's floor trails `max(day_start.peak, day_start.balance)` for `intraday` trailing, as `start_account` does.

Day roll (21.4): the first bar or fill (22.1) of a new trading day first applies one `DayClosed(previous day, bar.ts)` through `build_rules` for the account's phase (as the backtest: books the day into `closed_days` when traded, resets `day_start_balance`, `traded_today`, `halted_today`, trails an `end_of_day` floor), then sets `acct.day`, empties today's equity and resets `session.start`/`session_floor` to the new `day_start_balance` and floor. A `Breach` there halts open-ended (`halt_kind` "breach", reason `breach <rule>: <reason>`; it replaces a day halt, and also any open-ended halt that is not a breach, then with an `"alert"` `{message: "<breach reason> (was halted: <old reason>)"}` after its `"halt"`) and the account's figures stay as they were. Otherwise a sim or live `end_of_day` roll raises the peak to NinjaTrader's closing balance, or, when that floor would breach the app's own figures but not NinjaTrader's own equity, keeps them (with the peak raised to the app's own closing balance), halts with "confirm balances" and flattens any position the app holds (and the whole account while NinjaTrader shows open P&L), never a breach ("NinjaTrader figures (22.2)" below, #219). No other halt replaces an open-ended one. A day halt (`halt_day` set) whose day has passed lifts with an `"alert"` `{message: "halt lifted: <reason>"}`, and the bar's safety check runs against the new day's level; open-ended halts never lift. `setup.day_start` is not replaced at the roll: a sim/live runner that started without it keeps rejecting brackets (the hub never runs one: `start` sets it from NinjaTrader's first account message). A sim or live roll that is not a breach journals the new day's open as a `"day_start"` row `{day, balance: phase_start + day_start_balance, peak: phase_start + peak, ts}` after its other effects (the `end_of_day` peak raised first), so a restart later that day opens it at the same figures (#211).

Stale pause (21.4): `on_tick(s, now, stale_seconds)` pauses new entries (`RunnerState.stale` = reason, Bracket rejected with `paused: <reason>`) and writes one `"alert"` when the last bar closed more than `stale_seconds` ago while `now` and `now − (stale_seconds + 60 s)` are both `in_session`, so the reopen after the daily break or the weekend is not stale; the next bar clears it. `account_status` reports it as `halted: true`, `halt_kind: "stale"`, `halt_reason` = the reason, unless a halt is also set, which it shows instead. `stale_seconds` defaults to 180: bars exist only for minutes that trade and arrive a lag grace after their close, so at 90 a single quiet minute raised the pause.

Each sync re-reads `armed`: a removed or changed row stops that account (its child killed); a new row starts with `core.start(Setup(armed, sha256 of the file read with read_regular, with_dll(rules, armed.dll_on), spec, safety_margin_pct, rules_hash, instruments_hash, accounts.yaml dll_on), now, halts)` (`rules_hash`/`instruments_hash` from `fenrir.rules.loader.read_account`/`fenrir.core.instruments.read_instruments`: the sha256 of the very bytes parsed; `halts`: `journal.rows(conn, account, kind="halt", since=armed_at)` payloads) and `peaks` (the same for `kind="peak"`) (dry runs; sim and live wait for NinjaTrader, "Starting sim and live (#211)" below). A row whose rules, contract, `instruments.yaml` or `accounts.yaml` fails is `broken`: one `"alert"` `cannot start: <error>`, an AccountStatus with `halted: true`, `halt_kind: null` and null figures, retried only when the row changes. Strategy code runs in one `python -P -m fenrir.live.step_child <path>` per started account (DEC-1: `terminal.child_env`, `jobs_runner.strategy_user`, own session), which holds the strategy's state: it answers `{"hash"}` after `init` (60 s), then one `{"actions": [{type, **fields}]}` per `{"ctx": ctx_json(ctx)}` line (`step_timeout`, 10 s). A load error, a hash that is not `armed.strategy_hash`, or an isolation refusal halts the account (`cannot load the strategy: …`); a step error, timeout, EOF or a reply `parse_reply` refuses (unknown type or key, a non-number, NaN, Infinity, `1e999` or a number `float()` overflows) is `step_failed` and the child is killed; any other error in one account's bar halts that account alone (`live runner error: …`, child killed) and the other accounts still step; the halt is built from the state the hub last kept, so a breach whose own row failed to journal stays the halt (never replaced by `live runner error`). When sqlite refuses a write (locked past its busy timeout), the account stays halted in memory, the failure is logged, and the refused `"halt"`, `"peak"` and `"day_start"` rows (the ones `start` reads back) are kept and written again, oldest first, before that account's next effects (the next tick, within 5 s); disarming drops them. Remaining window (#182): if the process stops before sqlite takes a write again, those rows are lost and a restart does not restore that halt or peak. An account with no child still journals each bar (`"bar"`, 0 actions). Bars of other series or of a non-front-month contract are ignored; each account picks its front month (bars and fills) from the `instruments.yaml` it started with and pinned, never one another account's start read later, and an account whose front month cannot be found halts (`live runner error: …`) rather than skipping its bars unchecked. A bar or tick error is logged once per account and error (#211): a halted account whose front month cannot be found fails the same way on every bar. The lifespan starts no bar stream yet: 04.2 supplies `stream_bars` and 21.8 runs it.

Starting sim and live (#211, DEC-4a): a sim or live row with both `start_balance` and `peak_balance` is set up at sync (a failure is `broken`, as above) and then waits for NinjaTrader's next `{type: "account"}` stream message whose `id` is the account and whose `balance` is above 0 (the add-on sends one every 2 s per managed account), since `Start.balance` is NinjaTrader's balance now and nothing else gives it. A balance at or below 0 is not a figure yet (e.g. NinjaTrader before its account data loads): the row keeps waiting. While waiting it has no runner and no step child, journals nothing, sends nothing, takes no fills, and its AccountStatus is that of an account that cannot start (`halted: true`, `halt_kind: null`, null figures) with `halt_reason` `waiting for NinjaTrader: no account message with a balance above 0 for <account> yet; nothing is sent until one arrives`, or the reason of a kill that could not disarm it or of a disarm that could not finish (below); a changed or removed row drops it. A lost link changes nothing: it waits on. Before starting a waiting row, a message with a balance above 0 syncs `armed` as a bar or tick does (one at or below 0 does not, so a row that waits reads nothing every 2 s), so a row disarmed or re-armed since the last sync never starts on its old arming: a re-armed row is parked afresh, and this same message starts the new arming. The message then starts it: `Start(armed.start_balance, armed.peak_balance, message.balance, message.realized_pnl_today)` (so `phase_start` and the confirmed peak are the pins, and `core.start` raises the peak to the highest journalled one), `core.start` with the `"halt"`, `"peak"` and `"day_start"` payloads since `armed_at`, `core.replay` with today's rows, then `core.on_account` with that same message (NinjaTrader's figures, the sim/live mode check), and the step child as for any start; a failed strategy load adds its halt after those rows. It then reconciles on the next tick (5 s) as any unreconciled account. Today's open is today's journalled `"day_start"` row when there is one (each roll writes one, and so does a first start), so a restart mid-day opens the day where it opened, not at the balance at restart. Else (first start today, or the server was down over the open) it is the message's `balance − min(realized_pnl_today, 0)`: NinjaTrader's balance less any realized loss today, journalled as a `"day_start"` row with an `"alert"` saying so, and `replay` books today's journalled fills against it, never above NinjaTrader's balance. A morning loss therefore counts once (the open is the one DEC-4b's third stricter-of term assumes, so the three equity terms agree). A morning gain stays in the open: it gives no extra daily-loss room, which is stricter than the firm's DLL by the gain (fail-closed), and it is never cut from the app's balance, on the first start, on a restart the same day or after a roll. That also makes the open independent of when NinjaTrader resets `RealizedProfitLoss`: a stale figure from the day before can only make it stricter (a stale gain is left out, and a stale loss raises the open, which leaves less daily room). A first balance at or below the liquidation level from the pins does not start: it halts with "confirm balances" (open-ended, `halt_kind` null, never a breach; `start` above), with no strategy loaded and null figures. Such a balance may be a real breach or a bad figure, and only the user can tell, by re-arming with the confirmed balances. A sim or live row missing either balance (none can be armed so, 23.3) starts at once and `core.start` halts it with the DEC-4a reason. A row armed before #211 has the old DEC-4a halt row journalled since its `armed_at`, which `start` restores: it stays halted until re-armed. Dry runs start at once, as before.

Order routing (22.4), in `LiveHub`: a new row starts with `core.start`, then `core.replay` with today's rows since `armed_at` (`journal.rows(conn, account, day=trading_day(now), since=armed_at)` as `(kind, payload)`). Effects run in order: each `Log` is journalled and each `Send` posted, Bracket → `addon.bracket(client_id, account, nt_instrument(spec.symbol, the bar's front month), side, int(qty), stop, target)`, Flatten → `addon.flatten(client_id, account)`. The post-effects state is kept before the first post, so an entry fill that arrives meanwhile finds its working entry. Only a definitive refusal goes through `core.send_failed` (the `"alert"` `send <client_id> failed: <error>`): `{accepted: false, duplicate: false}`, no add-on configured (`app.state.addon` None), a Bracket not posted because its row was refused (below), or a `duplicate` Bracket for which NinjaTrader's `/orders` show no entry order with its `client_id` and `/positions` no position on its instrument (the first attempt may have been refused and its reply lost; when that check itself fails it counts as landed). A `duplicate` Flatten has landed only when NinjaTrader's `/positions` then shows the account flat (22.5, #87): else, or when that check fails, it goes through `send_failed` (`send <client_id> failed: duplicate, but NinjaTrader still holds a position`), so a refused first attempt never leaves `exiting` set to hold back every later exit; the next bar sends a new Flatten, harmless if the first did land (`/flatten` never over-closes). After a timeout or any other error the order may have landed, so there is no `send_failed`: one `"alert"` `send <client_id> outcome unknown: <error>; …`; a Bracket stays working until its fill, the day roll or reconciliation, and a Flatten is resent under the same `client_id` on each later effect run of that account (a tick within 5 s) while `exiting` is still that id, with no further alert. When sqlite refuses a row, no later row of that run is tried (the `"halt"`, `"peak"` and `"day_start"` ones among it and after it are queued, as above, and the error is raised after the run): Flattens are still posted, Brackets are not. `stop()` tries once to write the queued rows before closing the db. `handle_fill(fill)` books the add-on's `fill` through `core.on_fill` only on a sim or live account it names and only on that account's armed instrument (`nt_instrument` of the front month on the fill's trading day); other fills are ignored. Status `drift`: `ok` is false while any account has a drift pause, `ticks` the largest of each account's last entry-fill distance from its LSE close, in ticks (null until an entry fills; not restored on a restart).

Orders and fills (22.1): for sim and live, `decide` follows each accepted Bracket or Flatten's `"action"` log with a `Send` under `client_id(account, bar.ts, index, action)`; dry runs never send, and a Cancel is never sent (as in the backtest it only drops a Bracket from the same bar, and `step` cannot know NinjaTrader's order ids). One Flatten is out at a time: a sent Flatten (the strategy's or the runner's) is `RunnerState.exiting` until the position is flat or reverses, the day rolls or `send_failed` names it; meanwhile, and while flat, the strategy's Flatten is journalled unsent. A bar whose close is more than `stale_seconds` before `now` (late or replayed) takes no Bracket (`bar closed <n>s ago (over <stale_seconds>s): no entry at its close`); exits still go out. A sent Bracket is `RunnerState.working` until its first entry fill (a fill carrying its client_id while flat: the add-on must stamp entry fills with the bracket's client_id), `send_failed` for its client_id, or the day roll; meanwhile Brackets are rejected with `entry <client_id> still working`. `on_fill(s, fill)` takes the add-on's validated `fill` message (the shell passes only this account's instrument): it rolls the day first when the fill is in a new trading day (so a day closes after its exit fills), journals `"fill"` (the message), moves the position (average entry; stop and target from the working bracket; a fill through zero, or an opening fill that is not the working entry's, leaves a position with no known stop or target, which the runner flattens at once with `client_id(account, fill ts, "f<n>", Flatten())` (n = today's fill count including this one, counting the buffered fills a reconcile's book already held (below), which are not booked, so each fill's Flatten has its own id and a replay of the same journalled fills gives the same ids), and again on the next bar (`"x"`) if that send fails; each such Flatten is journalled with an `"alert"` `{message: "flattening: position <qty> has no known stop"}` before its `"action"`), and applies `Fill(ts, qty, price, commission, realized gross)` with commission = the largest of the fill's, the rules' `commission_per_side × |qty|` and 0, then `TradeClosed` (pnl net of the trade's commissions, `same_bar` = same UTC minute) when the trade closes; today's fill times go to `session.fills`. Drawdown and the daily loss limit are checked on the Mark that `on_bar` applies to every bar (the backtest's worst/best/close marks capped at the stop and target; flat, a zero Mark checks realized P&L); when an exit filled during the bar, `on_bar` first marks the position held before it against the balance before it (`RunnerState.held`), as the backtest marks a bar before its exit (an exit fill that arrives after its own bar's `on_bar` is marked against the next bar instead: stricter than the backtest, never looser), and a `Breach` from a Fill or Mark halts open-ended (`"breach"`) with the event still booked by `fenrir.rules.ledger.book`. `halted_today` (daily loss limit) day-halts with `halt_kind` "safety" (reason `daily loss limit hit: no new entries today`). While holding a position, `on_bar` sends the runner's own Flatten once (`client_id(..., "x")`; `"action"` payload adds `reason`) on the bar that closes at or after `min(session.flat_by, "16:40")` (the backtest's flat-time exit; the add-on also flattens at 16:40), after the daily loss limit is hit, after a breach, or while the position has no known stop; it is not resent while `exiting` is set. A position still open at the day roll is a `flat_by` breach, as before, unless the runner is unreconciled (22.3, below). The first entry fill more than `DRIFT_TICKS` (4) ticks from the close the bracket was checked at sets `RunnerState.drift` with one `"halt"` row `{reason, kind: "drift", until: null}` (so a restart restores it; 22.3): Brackets are rejected with `paused: <reason>` and `account_status` reports `halt_kind: "drift"` (unless a halt or stale pause shows instead) until 22.3's resolve clears it. The entry is not re-checked against the limits at the fill price (the backtest does not either); the drift pause bounds the gap.

NinjaTrader figures (22.2): `on_account(s, account, now)` takes the add-on's validated `{type: "account", ...}` message for this account; the hub calls it for each stream `account` message whose `id` is a running account (22.5); until the first one, and from a lost link until the next, sim and live runners have no NinjaTrader figures. Dry runs ignore it. When `is_sim` disagrees with the armed mode (sim armed on a live account, or live on a sim one), the account halts open-ended (`mode mismatch: armed <mode>, NinjaTrader reports a <sim|live> account`, `halt_kind` null), journalled once. Otherwise it keeps the figures as `RunnerState.nt`, except that a `balance` at or below 0 is not a figure (NinjaTrader before its account data loads, e.g. after it restarts): the message is ignored and the last figures stand, so it raises no false safety-margin halt (#211). Units: NinjaTrader's `balance` is absolute dollars; the app's `AccountState` (and AccountStatus `balance`, `session.*`) is relative to phase start (`Start.phase_start`). Stricter of (DEC-4b): the pre-trade check, the safety margin and AccountStatus's `today_pnl` and `limits` use the account with its equity cut to the lowest of the app's equity, NinjaTrader's `balance + unrealized_pnl − phase_start`, and today's opening balance plus NinjaTrader's `realized_pnl_today + unrealized_pnl`, all against the app's floor; so the smaller drawdown distance and the worse today's P&L both count (when NinjaTrader's and the app's opening balances differ this is stricter than either alone, never looser). NinjaTrader's figures never raise a `Breach`: rule events stay the app's, as in the backtest. At start a first balance at or below the liquidation level halts with "confirm balances" instead, and a balance at or below 0 is not taken at all ("Starting sim and live", #211). Peaks (DEC-4a): the drawdown peak rises to NinjaTrader's `balance` at each day roll for `end_of_day` trailing, and to its `balance + unrealized_pnl` on each account message for `intraday` trailing, the floor trailing it as `drawdown.trail` does (with `locks_at`). A gap between the balances alone is never a breach at the roll (#219): when the floor from NinjaTrader's closing balance is at or above the app's own equity (which passed the `DayClosed` check on its own floor) while NinjaTrader's own equity (`balance + unrealized_pnl − phase_start`) is still above it, NinjaTrader booked P&L the app never saw as a fill (a trade on another instrument, or a fill while the server was down), so the roll does not raise to it: the app keeps its own figures, raises its peak to its own balance at the close instead (DEC-4a's balance, as for NinjaTrader's; so its floor is never looser than NinjaTrader's by more than the gap, and an open loss it holds over the close still breaches), journals its `"peak"` row at that peak (so a restart the same day rebuilds the same figures), and halts open-ended with `confirm balances: a gap at the end-of-day session close: NinjaTrader's balance <x.xx> puts the drawdown floor at <x.xx>, at or above the app's equity <x.xx> (P&L the app never booked: a trade on another instrument, or a fill while the server was down); any position the app holds is flattened, and the whole account while NinjaTrader shows open P&L; re-arm with the confirmed balances` (`halt_kind` null, journalled, so restored on restart until re-armed). Every gap halt's reason starts `confirm balances: a gap` (`core.GAP`). No entries go out while one holds, and `_exit` flattens on that bar and on every later bar while it holds and no Flatten is out (`exiting`; a reconcile, a refused send or a roll ends it, so the next bar sends one under a new id; also after a restart, which restores the halt's reason), with the halt's reason journalled on its `"action"` row: a position the app holds; and, with the app flat, the whole account while NinjaTrader's latest `unrealized_pnl` is not 0 (to the cent): a position the app does not know of (a manual trade, another instrument), which the add-on's account-wide `/flatten` closes (#229). An account message with the app flat and no open P&L at NinjaTrader ends that Flatten (`exiting` cleared). A flat account whose NinjaTrader shows no open P&L sends nothing, and with no NinjaTrader figures (a lost link) only a position the app holds is flattened. The app's own drawdown checks still run: a real loss through its floor is still a breach, which replaces the halt. When NinjaTrader's own equity is at or below that floor too (an open loss it still holds over the close, e.g. an unverified position after a lost link), it is no gap: the roll takes the raise and the next Mark breaches and flattens, as before. A smaller gap (e.g. NinjaTrader's lower commission) only raises the floor, stricter by the gap, as before. A restart on a later trading day while that halt holds (no `day_start` row for that day) starts from NinjaTrader's balance, which holds the gap, with the app's journalled peak: its floor is then looser than NinjaTrader's by up to the gap, and the drawdown breach check itself runs on that floor, not only AccountStatus's `drawdown_remaining`, until re-armed. No entries go out, and a position the app holds or adopts is flattened under the restored halt; a manual position it never learns of is not. #225 tracks journalling NinjaTrader's raised peak next to the app's so such a restart takes the stricter of the two. The same holds for `intraday` trailing on each account message (#222): when the floor from NinjaTrader's `balance + unrealized_pnl` is at or above the app's equity (balance plus close-mark open P&L) while the app's own floor is below it, the raise is not taken (NinjaTrader's own equity is the peak it sets, so it is always above that floor): the app keeps its own figures with its peak raised to at least its own balance (an intraday peak is never below the balance), journals a `"peak"` row if that raised it, and halts open-ended with `confirm balances: a gap on NinjaTrader's account figures: NinjaTrader's equity <x.xx> puts the drawdown floor at <x.xx>, at or above the app's equity <x.xx> (…)` with the same tail, flattening as above. Each later message checks again, and the halt is journalled once. On a same-day restart of an `intraday` account (today's `"day_start"` row journalled, so `replay` sets the app's balance), `start` takes the journalled peak and does not raise it to NinjaTrader's balance: a balance above the journalled peaks is P&L the app never saw, which the account message after `replay` checks as above; a first start today (no row) still starts the peak at least at the balance. A sim or live account journals `"peak"` `{peak: phase_start + peak, ts}` (`ts` = the bar, fill or message that set it, UTC ISO 8601): for `end_of_day` trailing once at every day roll that has NinjaTrader's balance, raised or not (the roll's other effects first), and at no other time; for `intraday` trailing at every raise, NinjaTrader's (on `on_account`) or the app's own (a Mark, after the bar's other effects), and at `start` when the peak starts at the balance above the armed and journalled peaks. `start(setup, now, halts, peaks)` starts from the highest of `start.peak` and the journalled peaks (`day_start.peak`, the open's floor, is left as given). For `end_of_day` trailing, the last roll is the trading day of the latest `"peak"` row's `ts` (or of `armed_at` when there is none); no other row counts, so a stale-data alert or a `cannot start` row after the close proves nothing. When a trading day with a session (Monday to Friday, CME holidays included) after that one has opened (18:00 ET the evening before) by `now`, a close was missed whose balance may have moved since, and the account halts open-ended with `confirm balances: an end-of-day session close passed while the runner was down; re-arm with the confirmed peak balance` (`halt_kind` null). That halt is journalled, so it is restored on later restarts (#169), and only re-arming with a confirmed `peak_balance` (a fresh `armed_at`) clears it. A restart from Friday 17:00 ET to Sunday 18:00 ET does not halt: nothing trades before the Sunday open, and the roll at that open raises the peak to Friday's closing balance. A sim or live `end_of_day` roll with no NinjaTrader figures (`nt` is None: no account message yet, or dropped as stale by `on_disconnect` because the link was lost over the close) journals no row and halts the running account open-ended with `confirm balances: no NinjaTrader balance at the end-of-day session close; re-arm with the confirmed peak balance` (`halt_kind` null), journalled and so restored on restart: that close's balance is never taken, and a later restart would ask the same (22.5, #87). It also halts when the roll comes in the moment after a reconnect before NinjaTrader's next account message (every 2 s); that fails closed.

Link, reconcile, resolve and replay (22.3), all pure; dry runs ignore `on_disconnect` and `on_reconcile` and never pause for them. The hub runs `replay` on start (22.4, #86) and wires the rest (22.5, #87): on the stream's `connected` it sets `nt_connected` and, for every sim and live account, fetches `/positions` and `/orders` and calls `on_reconcile` (rows as `NtPosition(**row)` / `NtOrder(**row)`, `instrument` = `fenrir.bridge.names.nt_instrument` of the armed front month on today's trading day); each tick does the same for any account still `unreconciled` while `nt_connected` (armed or restarted while linked, or its last read failed), so a replayed `exiting` is cleared within 5 s; on `disconnected` it clears `nt_connected` and calls `on_disconnect(s, error)`; and `LiveHub.resolve(account)` (for `POST /api/live/resolve`, #88) calls `resolve` the same way. A failed read is logged and leaves the account paused. Stream `position` and `order` messages are not used (a reconcile reads the book itself; reconciling on each would race the bracket's own transitions, e.g. a fill before its OCO is placed reads as `missing_stop`). **Unreconciled pause:** sim and live start with `RunnerState.unreconciled` = `UNRECONCILED` ("not reconciled with NinjaTrader yet: no new entries"), and `on_disconnect` sets `LINK_LOST` ("NinjaTrader link lost: no new entries until reconciled") with one `"alert"` `{message: "<LINK_LOST> (<error>)"}` per outage (again after any reconcile ends it). Brackets are rejected with `paused: <reason>`; AccountStatus shows it only as `halt_reason` (`halted` and `halt_kind` unchanged). Open positions keep their broker-side stop and target; Python sends no Flatten for the lost link (DEC-5). **`on_reconcile(s, instrument, positions, orders, now)`** compares `fenrir.bridge.reconcile(ExpectedBook(account, instrument, position.qty), positions, orders)`, leaving out the runner's working entry while NinjaTrader still works it (an order with `role` `"entry"` and its `client_id`); NinjaTrader is the source of truth, so the runner then: keeps `working` only while that entry order is there (an entry NinjaTrader rejected or cancelled after accepting no longer blocks entries); clears `exiting` (`/flatten` never over-closes, so a second one is harmless); takes NinjaTrader's net qty on `instrument` as its position (its own entry and trade start kept while qty and side match, else NinjaTrader's average price and `now`; fills missed while the link was down are not booked, NinjaTrader's figures still count through the stricter-of checks), with stop and target = the price of the `"stop"` / `"target"` orders that close it and together cover exactly its qty (the furthest from entry when several), else None. Every reconcile clears `unreconciled`, mismatch or not (NinjaTrader just reported the book, so the position is verified and the next lost link alerts again). **Buffered fills (22.5):** each reconcile stores its `now` (taken before the reads) as `RunnerState.read_at`; `on_fill` journals, but does not book, a fill stamped at or before it, as NinjaTrader's book already holds it (stream messages that arrive while the hub reads the book are handled after the reconcile, and would otherwise be booked twice: an entry fill doubling an adopted position, or a stop fill opening a phantom one). It still rolls the day and counts as one of today's fills (`session.fills` and the `"f<n>"` ids, as a replay counts it). `replay` books every journalled fill whatever `read_at` says and keeps it. Limits: the cut-off is the server's clock taken just before the reads, on every path (connect, tick and Resolve take it after the hub lock and the tick's sync, never before them), against NinjaTrader's fill stamps, so a fill is misjudged when it lands between `read_at` and the moment NinjaTrader answers `/positions` (the read's latency: up to about 15 s when the client retries) or within the two clocks' skew of the read (NinjaTrader on a Windows VM with loose time sync can be seconds off). A fill already in the book but stamped after `read_at` (the latency, or NinjaTrader's clock ahead) is booked again: an entry doubles the adopted position, at worst a false halt or an early Flatten of a real position. A fill stamped at or before `read_at` but not in the book (NinjaTrader's clock behind, a real fill just after the read) is not booked: an entry leaves the runner flat with `working` held (the broker's OCO still protects the position, and the stricter-of checks still see NinjaTrader's figures), and its exit fill then opens a phantom position, flattened as stopless (harmless against a flat account) and a `flat_by` breach at the day roll. Both fail closed. Nothing corrects either on its own: a misjudged fill sets no mismatch, and on a stable link nothing reconciles again until the next reconnect (or a tick while the account is still unreconciled) or the user's Resolve. Not done: taking the cut-off from NinjaTrader's own clock (the last stream `ts` seen before the read) would remove the skew but not the read's latency, and that `ts` trails the read by up to the 2 s heartbeat, which widens the double-booking side. A mismatch sets `RunnerState.mismatch` = `NinjaTrader mismatch: <kind>: <detail>; …; fix it there, then resolve` (Mismatch kinds in `reconcile`'s order), journalled as a `"halt"` row `{reason, kind: "reconcile", until: null}` whenever the reason changes: Brackets are rejected with `paused: <reason>` until the user resolves it, even when a later reconnect matches. **Fail-safe (SPEC conflict, decided here):** when the position it takes has no covering stop (a manual trade, a manual add the OCO was not resized for: held qty ≠ OCO qty is `missing_stop`), the runner also flattens it at once (`client_id(account, now, f"r{now.timestamp()}", Flatten())`: each reconcile is a fresh read of NinjaTrader, so two in one minute get two ids, `"alert"` `flattening: position <qty> has no known stop` before its `"action"`), as `on_fill` does; the pause still waits for resolve. This applies to the armed instrument only: a position on another instrument is `unexpected_position` and only pauses. Strays are never cancelled. An adopted stop is not checked against the account's limits: a manual trade's stop beyond the drawdown floor is carried as is, with the drawdown checks on every Mark as for any position. **Unverified flat-by:** while `unreconciled`, a `flat_by` Breach on a Mark or at the day roll is not a breach, since the exit fill may have been missed while the link was down (the add-on flattens at 16:40 on its own): the event applies through the rules as if flat (a drawdown breach still halts), the account keeps its position, and it pauses with mismatch `unverified position: <flat_by reason>; reconcile with NinjaTrader, then resolve`. A fill past flat-by is NinjaTrader's own report and still breaches. **`resolve(s, instrument, positions, orders, now)`** lifts the reconcile and drift pauses, journalling `"halt"` `{reason: "resolved: <lifted reasons>", kind: "resolve", until: null}` when one was set (so a restart keeps them lifted: `start` restores `"reconcile"` and `"drift"` rows as those pauses and lets a `"resolve"` row lift both), then calls `on_reconcile` with the fresh book (a mismatch left pauses again, after the lift row). It never touches `halted`: a breach, safety, mode-mismatch or any other halt stays. AccountStatus `halt_kind` is `"reconcile"` while `mismatch` is set (a halt shows instead; it shows over stale and drift). **`replay(s, rows)`** (after `start` on a restart, before `on_reconcile`): `rows` are today's journal rows since `armed_at` (`journal.rows(conn, account, day=today, since=armed_at)`) as `(kind, payload)`, oldest first. A sent Bracket `"action"` becomes `working` (its close from the last `"bar"` row), a sent Flatten `exiting`, and each `"fill"` goes through `on_fill`, so position, average entry, stop and target, P&L, `fills`, `opened` and the fill-Flatten ids come back as they were live; the balance never loosens NinjaTrader's at the restart, which holds every fill (also those made while the runner was down and never journalled): with `day_start` it is the lower of today's opening balance plus the replayed fills (at the rules' commission) and NinjaTrader's, with `traded_today` true when either says so; without `day_start` it stays NinjaTrader's, with `start`'s `traded_today`; `opened_balance` moves by the same amount. No effects (every row was journalled); `drift` stays as `start` restored it, `held` is cleared, and sim and live stay `unreconciled` until `on_reconcile`.

Event stream and kill switch (22.5, #87), in `LiveHub`: `start()` also runs `run_stream` when an add-on is configured; should following the stream itself fail (anything `AddonClient.stream()` does not turn into `disconnected`), `run_stream` applies `{type: "disconnected", error: "stream follower failed: <ExceptionType>"}` (every account paused, `nt_connected` false; the type only, as the stream URL carries the token) and follows it again after 5 s; `stop()` logs any task's failure by type. `handle_stream(msg)` takes each `AddonClient.stream()` item: `heartbeat` sets `last_heartbeat` (its `ts`), `fill` goes to `handle_fill`, `account` to `core.on_account` for the running account (`armed.account`) equal to its `id`, or starts the waiting one (#211, above), `connected`/`disconnected` as above; an error in one message is logged and the next still runs. Each event (tick, bar, stream message) runs every account at once (`asyncio.gather`), so one account's slow add-on post never holds back another account's Flatten in the same event; the hub lock still spans the event, so the next event (e.g. another account's fill) waits for that post, bounded by the client's retries (3 × 5 s plus backoff, and 2 × 5 s for a `duplicate` check); the broker-side stop covers the position meanwhile. **`kill()`** (for `POST /api/live/kill`, #88, #206): first posts `/flatten-all` at once, before taking the hub lock, so an event holding the lock (a new account's strategy load up to 60 s each, a step 10 s, a hung post about 25 s) never delays it (two things still can: a hanging add-on, which this post goes to as well, and a sqlite write blocked on the event loop, e.g. by the arm route's `BEGIN IMMEDIATE`, for up to the 5 s busy timeout); then, under the hub lock so no bar or fill runs during the rest, posts `/flatten-all` again, which closes anything a bar opened while the kill waited for the lock (a Bracket posted after the first flatten), and nothing can open a position after this second one: under the lock no bar steps, and the lock is released only once every account is disarmed and stopped, or halted. Each post has a fresh `client_id` (`kill-<16 hex>`, so each is its own request and a retry inside the client is deduped). Then, as the disarm route does, journals per armed account its `"halt"` `{reason: "disarmed", kind: null, until: null}` before deleting every `armed` row (`arming.delete_armed`; dry, sim and live), and syncs (every runner stopped, every step child killed), so nothing is sent after the second flatten; then journals per disarmed account an `"alert"` `{message: "kill switch: disarmed; flattened and cancelled all"}` (or `…; <flatten error>` as in `error` below, or `…; flatten all failed: NinjaTrader add-on not configured (FENRIR_NT_TOKEN)`); an error writing the alert is logged, not raised. A halt row that cannot be written is reported (`halt rows not journalled: <error>`) but the deletes still go ahead: a deleted row can neither run nor restart. When the disarm itself fails (reading `armed`, or a delete; e.g. sqlite locked by the arm route), every running account is halted in memory instead (`kill switch: disarm failed[ for <accounts left>]: <error>`, its row queued and retried), and so is any row armed by the time the kill read `armed` (`armed_at` at or before it) that is not running yet (armed in the last tick's 5 s): the kill does not sync then (a sync would start, and load the strategy of, such rows before the kill answers), so the next tick (or bar) starts it halted with the same reason, journalled then, without loading its strategy, and stops any running account whose row the kill did delete; a sim or live row still waiting for NinjaTrader shows that reason as its `halt_reason` and starts the same way on NinjaTrader's message (#211); a `"disarmed"` row written before a failed delete halts it on every later start too. So none takes a new entry until disarmed. When the rows are deleted but stopping the runners fails, the running accounts are halted in memory (`kill switch: disarmed, but stopping the runners failed: <error>`) until the next sync stops them. The kill's time is kept in memory only: should the server restart before that tick, a row whose `"disarmed"` row was never written starts unhalted. Returns `{ok: true, error: null}`, or `ok: false` with the errors joined by `; ` when either `/flatten-all` was refused or failed (unreachable, timeout, HTTP status), named by which: `first flatten-all (before the lock) failed: <error>; the second landed`, `second flatten-all (under the lock) failed: <error>`, `both flatten-alls failed: <error>` (the same error twice, named once) or both labelled errors joined by `; `, when no add-on is configured while a sim or live account was armed or running (with only dry runs and no add-on there is nothing to flatten), or when reading `armed`, a halt row, a delete or stopping the runners failed. Known limits: only the first flatten is immediate; the second flatten, the disarm and the answer still wait for the hub lock behind an event in flight (a new account's strategy load holds it up to 60 s each, a step 10 s, a hung post about 25 s), and with the add-on unreachable both posts run to the client's retries; an arm that lands after the kill read `armed` is a later user action and stands.

**`disarm(account)`** (for `POST /api/arming/disarm`, #223; owner decision: disarming a sim or live account with an open position flattens it) follows the kill's order for one account. When `armed` holds the account in sim or live mode, it first posts the account's `/flatten` at once, before taking the hub lock. Under the lock it then re-reads the row (`{ok: false, error: null}` when the account is not armed, with nothing written and nothing more sent; in a race, when a kill or another disarm emptied the row after this disarm's first `/flatten`, that flatten has already gone out). For sim or live it posts `/flatten` again, which closes anything a bar opened while the disarm waited for the lock. Then it journals the `"halt"` `{reason: "disarmed", kind: null, until: null}` and deletes the row in one transaction (`arming.disarm`) and syncs, so the runner is stopped and its child killed before the lock is released. Nothing can open a position after that second flatten. Each post has a fresh `client_id` (`disarm-<16 hex>`), and `accepted` or `duplicate` counts as landed. The flatten under the lock decides: a failed first post whose second landed is only logged. One `/flatten` covers both the position and the working orders: the add-on closes whatever is open and cancels every Fenrir working order (entry, stop, target) on the account, and every working order on an instrument it flattens (Plan 19/20 above). So a flat account still has its Fenrir working orders cancelled. A non-Fenrir order on an instrument with neither a position nor a Fenrir order is a stray and is left alone, as reconciliation leaves strays. A sim or live disarm journals an `"alert"` `{message: "disarmed; flattened, working orders cancelled"}` after the delete (an error writing it is logged, not raised). Dry runs never post. **Fail closed (decided in #223):** when the flatten under the lock does not land (refused, `"refused"` when the add-on gave no reason; unreachable, timeout, HTTP status or malformed reply as `<ExceptionType>: <message>`; or no add-on configured, `NinjaTrader add-on not configured (FENRIR_NT_TOKEN)`), the row is kept, nothing is deleted, and the account is halted with `disarm failed: flatten failed: <error>; the position may still be open: check NinjaTrader; still armed, halted until disarmed` (open-ended, `halt_kind` null). The halt is journalled as a `"halt"` row with an `"alert"` carrying the same message, and the answer is `{ok: false, error: <that message>}`. A running account is halted through `core.halt` (in memory even when sqlite refuses its row, which is then queued and retried, and the answer's `error` adds `; halt held in memory, not journalled yet (retried each tick; a restart before then lifts it): <ExceptionType>: <message>`). A row not running yet (armed since the last sync, waiting for NinjaTrader, or broken) gets the two rows journalled, so it starts halted, and a restart keeps any of them halted. Its halt is also held in memory as the kill's is (#227): the account's (time, reason), so its row, armed by then, starts halted with that reason without loading its strategy, a sim or live row waiting for NinjaTrader shows it as its `halt_reason`, and a re-arm after it starts free (a disarm that lands clears it). When sqlite refuses that `"halt"` row too (a failed flatten and a locked database at once), neither row is written, the held halt is journalled when the row starts, and the answer's `error` adds `; halt held in memory, not journalled (a restart before it starts lifts it): <ExceptionType>: <message>`: should the server restart before the row starts, it starts unhalted. Kept armed, a running account still marks every bar, breaches, and sends the runner's own Flatten at flat-by or after a breach, and the Live page shows it halted with that reason. It takes no new entry until the user disarms it again or presses the kill switch, which disarms whatever its flatten-all does. A read of `armed` that fails under the lock comes before the flatten under the lock, so none may have gone out (when sqlite fails, the read before the lock usually fails too and nothing is posted): it is kept the same way, with `disarm failed: cannot read the armed accounts: <ExceptionType>: <message>; not flattened under the lock: the position may still be open: check NinjaTrader; still armed, halted until disarmed`. A disarm write that fails after the flatten under the lock landed (e.g. sqlite locked by the arm route) is kept the same way, with the error as the cause (`disarm failed: <ExceptionType>: <message>; still armed, …`). When the row is deleted but the sync fails, a still-running account is halted in memory (`disarmed, but stopping the runner failed: <error>`) until the next sync stops it, and the answer is `ok: false` with that error. Known limit: as for the kill, the second flatten, the disarm and the answer wait for the hub lock behind an event in flight.

Arm details (23.2): `mode` and `phase` are validated as literals, `confirm` and `dll_on` as strict booleans (`"yes"` or `1` is a 422), and the balances as finite numbers > 0 (422, as is a `ValueError` from `decide`); `400` also for a path that is not a `.py` file directly in `strategies_dir`, a symlink, a missing or unreadable file, or a symlinked `strategies_dir` (the file is hashed with `read_regular`, never imported); `502 nt_unavailable` also when no add-on is configured or its reply is malformed (also for `GET /api/arming/accounts`); `500 {detail}` for a broken cached report or `accounts.yaml`. `list_armed` → `decide` → `insert_armed` run inside one `BEGIN IMMEDIATE` transaction, so two concurrent arms of one account give one `200` and one `409 already_armed`. `armed_at` is the time of the arm, so a re-arm (disarm, then arm) starts a fresh window for the halts and peaks `start` restores. `start_balance`/`peak_balance` are validated here and stored on `armed` (23.3). `GET /api/arming` is `[]` while `fenrir.db` does not exist (read on `open_ro`, never creating it). The hub picks up an arm on its next tick (5 s; it re-reads `armed` every tick and bar); a disarm stops the runner before it answers (#223). No CLI command arms or disarms (`tests/cli/test_main.py::test_no_cli_command_arms_or_disarms`).
