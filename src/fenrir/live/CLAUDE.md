# src/fenrir/live/

Runs armed strategies on live bars: decides per bar, checks limits, journals every decision and stores which strategy is armed on each account. Rolls the trading day (lifting day halts), pauses entries on stale data, emits the orders to send (`Send`), books the add-on's fills, and checks limits against the stricter of its own and NinjaTrader's account figures (halting on a sim/live mode mismatch). Sim and live take no new entries until NinjaTrader's book is reconciled (on start and after a lost link); a mismatch pauses entries until the user resolves it, and a restart replays today's journalled orders and fills. `LiveHub` runs it all for the server: it posts the `Send`s to the NinjaTrader add-on, books the fills routed to it and replays the journal on start (22.4), follows the add-on's event stream (reconcile on connect and while unreconciled, pause on a lost link, account figures, fills) and holds the Resolve and kill-switch actions (22.5).

- Entry points: `core.py` (pure runner: `start`, `on_bar`, `on_tick`, `on_fill`, `on_account`, `send_failed`, `on_disconnect`, `on_reconcile`, `resolve`, `replay`, `client_id`, `in_session`, `runs_step`, `ctx`, `decide`, `step_failed`, `halt`, `changed_since_arming`, `account_status`, `safety_level`, `start_account`; `Setup`, `Start`, `NtAccount`, `RunnerState`, `Working`, `Log`, `Send`), `journal.py` (`open_db` creates `journal` and `armed` in `<private_dir>/fenrir.db`, in WAL mode so readers never block the hub's writes, and adds the 23.3 pinned columns to an older `armed`; `open_ro` for readers, never creating the file; `write`, `insert` (no commit, for a caller's transaction), `rows`, `day_bounds`, `JournalRow`, `KINDS`), `arming.py` (`Armed` with its pins (`dll_on`, `rules_hash`, `instruments_hash`, balances; DEC-4d), `list_armed`/`insert_armed` by column name, `delete_armed`, `disarm` (halt row and delete in one transaction); `ArmRequest`, `Refusal`, `decide`: may this file be armed on this account, one `Refusal` per 409 reason; `liquidation_level` for the live confirmation), `service.py` (`LiveHub(settings, *, secret, step_timeout, addon)`: `start`/`stop` from the server lifespan, `tick`, `handle_bar`, `handle_fill`, `handle_stream`, `resolve(account)`, `kill()`, `status`; `run_ticks`, `run_stream(hub)`, `run_bars(hub, stream)`; pure `parse_reply`), `step_child.py` (`python -P -m fenrir.live.step_child PATH`: one per started account, holds the strategy's state; pure `ctx_json`/`parse_ctx`).
- Pure vs shell: `core.py` is pure `(RunnerState, input) -> (RunnerState, effects)` and never imports strategy code: the shell runs `step(ctx(state))` in a child (DEC-1) and passes the actions to `decide`. `journal.py`, `arming.py` and `service.py` are shell (SQLite I/O, child processes, add-on posts; the hub opens `<private_dir>/fenrir.db` only once it exists, never at app build); `day_bounds` and `decide` are pure (the caller passes `list_armed`, reports, NinjaTrader's `is_sim`, account choices and `now`).
- Pre-trade decisions must match the backtest's (`fenrir.backtest.attempt._act`); `test_accepts_exactly_what_the_backtest_accepts` pins it.
- `step` sees the backtest's bars: no roll-window bar reaches `step` or `Ctx.bars` (`runs_step`), though `on_bar` still marks and flattens on it; `test_step_sees_the_bars_the_backtest_shows_it_around_a_roll` pins it.
- Fills book the account like the backtest (`attempt._open`/`_close`/`_mark`); `test_live_fills_book_like_the_backtest` pins it. Dry runs never emit a `Send`.
- Pinned inputs (DEC-4d): `core.changed_since_arming` halts an account whose strategy, rules or `instruments.yaml` hash, or `accounts.yaml` `dll_on`, is not what `armed` pinned (or that has no pins), at `start` and on every bar while armed; the hub hashes the very bytes it parses (`read_account`, `read_instruments`) and keeps each account's own `Instruments`. A new input the runner depends on gets pinned the same way, and any per-bar error halts the account, never leaves it unchecked.
- Halts and pauses that must survive a restart are journalled as `"halt"` rows, which `start` restores; anything that lifts one in place (e.g. `resolve`) journals a row `start` understands, or the next restart brings it back.
- Never add a CLI command that arms or disarms, and never write the `armed` table outside `arming.py` (SPEC: arming is user-only; the hub disarms only through `arming.delete_armed`, on the user's kill switch).
- Not here: arm/disarm endpoints (`src/fenrir/server/routes/arming.py`); the add-on client (`src/fenrir/bridge/`); rule math (`src/fenrir/rules/`).
- Tests: `tests/live/` (shared helpers in `tests/live/live_helpers.py`, imported by name).
